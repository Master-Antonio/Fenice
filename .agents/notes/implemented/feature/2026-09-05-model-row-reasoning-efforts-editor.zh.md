# Agent Note: 模型行的推理等级编辑器

Status: implemented

[English](2026-09-05-model-row-reasoning-efforts-editor.md) | 中文

## 问题

pi-ai 模型的推理行为按模型配置：`reasoningEfforts` 字典列出模型提供的等级及每个等级在请求中发送的值，而且该字段是让手工声明的模型拥有推理能力的唯一途径。此前它只存在于 `settings.yaml` 中，每新增一个模型都要手写一个嵌套的 YAML 字典——缩进的映射、带引号的值、`off: null` 约定——Models 页面对模型行的其他一切皆可编辑，唯独这里毫无帮助。失败方式也很具体：真实的 settings 文件里出现过缩进错误（包括从其他编辑器粘贴进来的 tab），随后适配器在加载时拒绝该字典。

Composer 的模型选择器已经能按模型提供推理等级（来自适配器解析后的 catalog），但它改变的是单次会话的请求；它无法声明某个模型提供哪些等级，也无法拼写某个网关的 wire 值。此前"刻意不设推理控件"针对的是*提供方级*控件——它只能为意见不一致的模型们存一个值；按模型的控件没有这个缺陷。

## 决策

pi-ai 模型行的高级折叠区——已承载上下文窗口与最大输出 token 的那个——现在编辑该行的 `reasoningEfforts`（`packages/client/ui-settings-models`）。一个选择框与适配器的解析语义一一对应：**提供方默认**移除该字段（已安装 catalog 的能力生效；手工声明的模型由此没有推理）；**禁用**存入 `false`（非推理模型）；**自定义等级**为每个等级生成一行，带复选框与 wire 值输入框。`off` 的值留空存为 `null`——"支持，但不发送参数"；`off` 以外的等级留空则撤销该等级，而不是存入适配器会拒绝的值。选择自定义时按每个 schema 等级预填、拼写取等级名本身——这几乎是所有 OpenAI 兼容网关都接受的形状。

提供的等级在渲染时从适配器自身的 schema 读取——探测模型行上 `reasoningEfforts` 字典的 key union，与本页面读取 wire 协议选项用的是同一个 schema 读取（`store.ts` 中的 `reasoningLevelChoices`，沿 `providers.<route>.api` 的模式）。客户端不拥有任何等级词汇表：pi-ai 升级新增等级时页面无需改动即随之出现，页面也永远不可能提供适配器无法派发的等级。schema 未声明推理字段时，控件直接隐藏而非以空列表呈现。

校验并入共享的按行检查器（`validateDeepSeekModels`），它现在也会拒绝适配器解析阶段拒绝、而序列化 schema 无法表达的情况：字典中没有 `off` 以外的等级，或 `off` 以外的等级没有 wire 值。Host 的 `settings-rejected` 校验器仍是权威；行级失败的意义在于让提交按钮被禁用、消息指向可见的行而非 settings 路径。

## 已考虑的替代方案

**在卡片上放一个提供方级的等级选择框。** 因已记录的理由被拒绝：同一提供方下的模型对推理能力意见不一，一个控件只能存入部分模型会拒绝的值；何况 pi-ai 的能力本来就按模型存放。

**在模型发现时从提供方的 HTTP 端点抓取等级。** 没有任何 listing 端点会报告模型的推理协议；权威来源只有适配器的 catalog 与其配置 schema，抓取等于编造数据。对已安装 catalog 的模型，正确答案是"继承"模式——读取 catalog 能力而不把它复制进 settings。

**用 catalog 的推理能力预填新采纳的行。** 没有必要：不带该字段的行会继承已安装 catalog 条目的能力，写入字典只会冻结一份副本，之后的 catalog 更新反而不再跟随。

## 后果

- 这个页面本来要消灭的 `settings.yaml` 手工编辑——嵌套的按模型字典及其引号与缩进规则——在常见场景下消失了；存储文档的形状不变，因此没有迁移或兼容行为。
- schema 读取模式现有两个消费方（协议、推理等级）。两者都失败关闭：schema 读不出来就隐藏控件，而不是猜测一份词汇表。
- 按行校验类型新增两个消息键，两个适配器家族的卡片共享；DeepSeek 家族没有该字段、其行也不携带，因此该校验在那里是空操作。
- 手工声明提供方的创建卡片经其模型列表获得同样的编辑器——新模型的推理往往正是在这里首次声明。
